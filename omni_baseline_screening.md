# Omni-Model Baseline Screening — SurgViVQA-Audio

**Purpose:** identify an off-the-shelf omni model that can answer the same task as
SurgViVQA-Audio (spoken question + 8 video frames → short text answer), to serve as a
zero-shot comparator. Screening is desk research plus a cheap on-pod probe. No full
evaluation run is authorized until a candidate clears both.

**Date of screen:** 2026-07-28 · **Live re-verification:** 2026-07-29
**Scope:** **probe Phi-4 + MiniCPM-o 4.5, run one** (decision table in
`PRE_REGISTRATION.md` §3.1). Everything else is screened and scoped but **not run and not
probed.**
**Screened by:** desk research (model cards, repos, issue trackers) — every claim below is
sourced, and every claim marked ⚠️ is *unverified* and must be settled by the probe script.

## Screening criteria

A candidate must pass **all five**:

1. Accepts audio **and multiple images in the same prompt** — the *combined* path, verified,
   not the two modalities documented separately.
2. Runs on a single 48 GB card, or the quantization required is stated explicitly.
3. Open weights.
4. Permissive license for portfolio use.
5. A working reference implementation for audio+image exists.

Plus a hard constraint that is not a screening criterion but a disqualifier at run time:

6. **Prompt parity** — the question must reach the model through audio only. No question
   text in the prompt, the instruction string, the system prompt, or anything the chat
   template injects.

**No parameter discrepancy.** 9B × 2 bytes ≈ 18 GB weights + ~2 GB repo assets = 20 GB.

enumerated; the derivation above is from repo total and stated param count.)

### Criterion 1 — RESOLVED IN FAVOUR, and it flips the earlier ⚠️

The desk screen flagged a conflict: an MLX port's card said "one image per turn, one audio
clip per turn." **That was the port, not the model.** The live card documents a
*Structured Content Input* section with a single content list mixing modalities:

```python
msgs = [{"role": "user", "content": [pil_image, audio_ndarray, "Describe this."]}]
```

plus a documented multi-image path (`[image1, image2, question]`) and a video-as-frames
path (`video_frames + [question]`, with `use_image_id=False, max_slice_nums=1`). An
OpenAI-style form accepts `image_url` / `audio_url` / `text` in one array.

8 frames + 1 audio array + instruction in one content list is therefore **documented**.
Still probed rather than assumed — that is what the screen is for.

### The three things that will bite

**1. Its own transformers pin, and it conflicts with Phi-4's.** The card requires
`transformers==4.51.0` exactly — "other versions may have compatibility issues (under
investigation)". Phi-4 requires 4.48.2. **Two venvs, confirmed by document, not assumed.**
torch 2.6.0 satisfies both ranges, so torch can be shared.

**2. eager is not available.** MiniCPM supports `sdpa` or `flash_attention_2` and *not*
eager. So "skip flash-attn on both" is honoured via **sdpa** for MiniCPM-o — torch-native,
no compiled wheel, no build. Same intent, model-legal.

**3. Thinking mode ships in the same checkpoint.** Instruct and thinking modes are one
model. `enable_thinking=False` is mandatory; a reasoning trace ahead of a one-word answer
destroys exact-match scoring. Also `init_tts=False`, `use_tts_template=False` for text-only
output, `use_image_id=False`, `max_slice_nums=1` per the card's own multi-frame example.

Audio must be 16 kHz mono float via `librosa.load(path, sr=16000, mono=True)`; **ffmpeg is
required** to decode the project's `.mp3` clips.

**`omni_mode`** — the card's omni examples interleave frame/audio-segment pairs synced on a
timeline (TDM). Ours is 8 static frames + one complete spoken question, i.e. the plain chat
path. `--omni-mode` probes the alternative if the plain path fails Gate 3b.

## PROBE CANDIDATE — Phi-4-multimodal-instruct

**Role: the safer run.** Architecturally parallel to SurgViVQA-Audio and smaller.
Frozen Phi-4-Mini backbone, separate vision and speech encoders each with a projector,
mixture-of-LoRAs. 5.6B against a Qwen2-VL + Whisper-large-v3-turbo stack. If a smaller
general-purpose model built the same way already does this task, that is the interview
answer, and it is better to know.

**Criterion 1 — combined path: PASS, and unusually cleanly.** The model card documents a
distinct *Vision-Speech Format*, separate from the vision-language and speech-language
formats, and gives the multi-image variant explicitly:

```
<|user|><|image_1|><|image_2|><|image_3|><|audio_1|><|end|><|assistant|>
```

Two things follow, and the second is the important one:

- Multi-image + audio is a first-class documented path, not an inference from
  "supports images" + "supports audio". Up to 64 frames are supported; 8 is comfortable.
- **The canonical template contains no instruction text at all.** The audio slot *is* the
  instruction. This is the cleanest prompt-parity case available in the candidate set —
  there is no instruction string to audit, because there isn't one. See the parity section
  below for why that is a mixed blessing.

**Criterion 2 — 48 GB: PASS with room.** 5.6B at BF16 ≈ 11.2 GB weights. Vision tokens
scale with crop count, so cap the per-frame resolution rather than letting 8 frames
negotiate their own budget. Tested by Microsoft on A6000 among others, which is the card
class in play.

**Criteria 3/4 — MIT license.** No ambiguity, no gated access, no acceptable-use rider.

**Criterion 5 — reference implementation:** `sample_inference_phi4mm.py` ships in the repo.

### The environment trap — read before renting

This is a direct analogue of the forked-transformers problem on this project, and it will
bite in the same silent way.

There are **two distinct code paths** for this model and they use **different prompt tokens**:

| Path | Loader | Placeholders | transformers |
|---|---|---|---|
| Remote code | `AutoModelForCausalLM(..., trust_remote_code=True)` | `<\|image_1\|>`, `<\|audio_1\|>` | pinned **4.48.2** |
| Native | `Phi4MultimodalForCausalLM` / `Phi4MultimodalProcessor` | different token scheme | recent |

The remote-code path **breaks on transformers ≥ 4.50** with
`AttributeError: 'Phi4MMModel' object has no attribute 'prepare_inputs_for_generation'`
(model card discussion #75). The documented requirements pin `transformers==4.48.2`,
`torch==2.6.0`, `flash_attn==2.7.4.post1`, Python 3.10.

The failure mode to fear is not the crash — a crash is honest. It is writing the
remote-code placeholder format into a native-path processor, having the placeholder pass
through as literal text, and getting a plausible-looking number off a prompt where the
audio was never attached. That is the same class of error that invalidated this project's
original result. **The audio-sensitivity probe in `verify_combined_path.py` is designed to
catch exactly this and must pass before any full run.**

Practical consequence: **Phi-4 and Gemma 4 cannot share a virtualenv.** Phi-4 wants
transformers 4.48.2; Gemma 4 needs a recent release. Two venvs, or two pod sessions.
Budget for it.

### Open question for the probe

Mixture-of-LoRAs means adapters are selected by input modality. Which adapter is active
when image *and* audio are both present is not something I will assert from the model card.
The probe answers it behaviourally: if swapping the audio changes the output, the speech
path is live, and the adapter question becomes an implementation detail rather than a
correctness risk.

## SCOPED BUT NOT RUN — Gemma 4 12B IT

**Status: not in scope.** Held pending Phi-4's number. Facts below are from the 2026-07-28
desk screen and have **not** been re-verified live — re-fetch before any use.

**Why it would be the natural second arm:** it is the *architectural opposite* of both
SurgViVQA-Audio and Phi-4.
Gemma 4 12B is **encoder-free** — it projects raw image patches and raw audio waveforms
straight into the LM embedding space through lightweight linear layers, with no Whisper,
no SigLIP, no separate encoder stack. SurgViVQA-Audio is Whisper-large-v3-turbo encoder →
linear projector → Qwen2-VL. Phi-4 is encoder + adapter + LoRA. Having all three points on
the design axis makes the eventual writeup a comparison of architectures rather than a
comparison of two arbitrary checkpoints.

- **License: Apache 2.0.** Note this is a change from the Gemma 1–3 custom license — worth
  double-checking on the repo page at run time, but the model cards state Apache 2.0.
- **Audio is only on E2B, E4B, and 12B.** The 26B A4B and 31B variants are image-only.
  Pulling a bigger Gemma 4 to be "safer" silently removes the modality under test.
- 12B dense at BF16 ≈ 24 GB. Fits.

**Two configuration items that are arm-defining and must be pinned:**

1. **Documented modality ordering is image → text → audio.** Our text slot is empty, so the
   layout is images, then audio. Do not reorder to match Phi-4's template; each model gets
   its own documented-optimal layout, and *that* is what parity means here — same
   information, each model's native format.
2. **Thinking mode must be off.** Gemma 4 has configurable thinking triggered by a `<|think|>`
   control token. A reasoning trace in front of a one-word answer will destroy exact-match
   scoring and produce a number that measures output format, not task ability. Pin it off,
   record the setting, and confirm in the dumped prompts.

Also: variable visual token budget (70/140/280/560/1120 per image). Pick one, write it down,
use the same one for all 1000 rows. The card recommends lower budgets for multi-frame work.

## Scoped, not probed

**Qwen2.5-Omni-7B (Apache 2.0)** — fits comfortably, mature tooling, GPTQ-Int4 and AWQ
variants exist but are unnecessary at 48 GB. Reserved because its documented strength is
*video with an interleaved audio track*, and the multiple-separate-images + separate-audio-file
path needs verifying. Two operational notes if promoted: call `disable_talker()` (we want
text out, saves ~2 GB), and keep `use_audio_in_video` consistent — it is a known
footgun. The prescribed system prompt is a fixed persona string with no question content, so
it does not threaten parity.

## Deprioritized, with reasons

**Qwen3-Omni-30B-A3B** (Apache 2.0, MoE 30B/3B active) — does not fit in BF16 on 48 GB.
Community AWQ-4bit does fit. Deprioritized not on capability but on **confound**: the
like-for-like arm is zero-shot vs zero-shot, and running the only quantized model in the
set introduces a variable that has nothing to do with architecture. If it goes in, it goes
in with the quantization stated in every table, and it is not the headline comparison.

**Nemotron 3 Nano Omni 30B-A3B** (commercial use permitted; CRADIO v4-H vision + Parakeet
speech encoders) — FP8 checkpoint is 32.8 GB and fits 48 GB; BF16 (~60 GB+) does not.
Deprioritized on three counts: quantization confound again, a serving stack that wants
sglang/vLLM with a specific CUDA 13 docker image rather than plain transformers, and it is
a **reasoning** model whose default output shape is hostile to short-answer exact match.
Real candidate for a later, better-funded round.

**Qwen3.5-Omni** — 2026 release, referenced widely, but open-weight availability and license
were not confirmable from primary sources during this screen; secondary coverage explicitly
warns against planning open-weight deployment before the official card confirms licensing.
Excluded on criterion 3/4 *pending verification*, not on merit. Recheck the Qwen HF org
before finalizing.

**MiMo V2 Omni (Xiaomi)** — appears as a priced API model on OpenRouter. No open-weights
release located. Fails criterion 3.

**Qwen3-ASR** — excluded by instruction and correctly so; transcription, not VQA.

## Recommendation

**Probe both, run one.** MiniCPM-o 4.5 preferred if both pass — it is a Whisper encoder
projected into an LLM, i.e. this project's own design built by a better-resourced team, so
it answers "is my design sound and what does the well-resourced version reach." Phi-4 is a
different design solving the same task and answers only "does something off-the-shelf do
this." Phi-4 is the safer run; MiniCPM-o is the informative one. Decision table in
`PRE_REGISTRATION.md` §3.1.

Gemma 4, Qwen2.5-Omni and Nemotron 3 Nano Omni stay scoped, unprobed and unrun.

The measurement is cheap. The only expensive thing in this project is reporting a number
